#### Объяснение результатов:

1. **Разница между Хартли и Шенноном:** Энтропия Хартли предполагает равновероятное появление всех символов алфавита (максимальная неопределённость). Энтропия Шеннона учитывает реальные частоты — в естественных текстах некоторые символы встречаются чаще других, что снижает энтропию.

2. **Избыточность исходного текста (21.23%)** — типична для естественного языка на UTF-8: кириллица кодируется 2 байтами на символ, плюс пробелы, знаки препинания, повторяющиеся гласные создают статистическую избыточность.

3. **Избыточность base64 (12.06%) ниже** — base64 распределяет биты более равномерно по 64-символьному алфавиту, каждый символ несет ровно 6 бит информации. Padding (`=`) и особенности кодирования UTF-8 → base64 вносят небольшую избыточность.

4. **Фамилия vs имя:** У фамилии выше избыточность из-за повторяющихся байт (UTF-8 кодирует кириллицу 2 байтами, старшие биты одинаковы), имя короче и более «случайно» выглядит на байтовом уровне.

### 3. XOR операций

#### Входные данные:
- **a (фамилия):** "Иванов" → UTF-8: `d0 98 d0 b2 d0 b0 d0 bd d0 be d0 b2` (12 байт)
- **b (имя):** "Петр" → UTF-8: `d0 9f d0 b5 d1 82 d1 80` (8 байт)

#### XOR в ASCII (UTF-8 байты):
```
a: d0 98 d0 b2 d0 b0 d0 bd d0 be d0 b2
b: d0 9f d0 b5 d1 82 d1 80 00 00 00 00  (дополнено нулями)
⊕: 00 07 00 07 01 32 01 3d d0 be d0 b2
```

#### XOR в base64:
- a_base64: `0JjQstCw0L3QvtCy` (16 байт ASCII)
- b_base64: `0J/QtdGC0YA=` (12 байт ASCII)
- XOR результат: `00 00 45 00 07 10 04 34 00 15 72 6c 76 74 43 79`

#### Проверка свойства a ⊕ b ⊕ b = a:
- **UTF-8:** `a ⊕ b ⊕ b = a` ✓ (True)
- **base64:** `a_b64 ⊕ b_b64 ⊕ b_b64 = a_b64` ✓ (True)

**Объяснение:** XOR — обратимая операция. Для любых битов: `x ⊕ y ⊕ y = x ⊕ (y ⊕ y) = x ⊕ 0 = x`. Это фундаментальное свойство используется в криптографии (одноразовый блокнот, потоковые шифры).

## Ответы на вопросы для контроля и самоконтроля

### 1. Что такое base64?

**Base64** — это алгоритм кодирования двоичных данных в текстовый формат, использующий 64 печатных символа ASCII (A-Z, a-z, 0-9, +, /) и символ заполнения `=`. Каждый символ base64 кодирует 6 бит исходных данных. Назначение — передача бинарных данных через каналы, поддерживающие только текст (email, URL, JSON, XML). Размер данных увеличивается на ~33% (4 символа на 3 байта).

---

### 2. Как проверить, была ли определенная строка закодирована в base64?

**Признаки base64:**
1. **Длина** кратна 4 (после добавления padding)
2. **Алфавит:** только символы `A-Z a-z 0-9 + / =`
3. **Padding:** 0, 1 или 2 символа `=` в конце (никогда не в середине)
4. **Нет пробелов/переносов строк** (в чистом виде; MIME-версия может иметь переносы каждые 76 символов)

**Проверка алгоритмически:**
```python
import re
def is_base64(s: str) -> bool:
    pattern = r'^[A-Za-z0-9+/]*={0,2}$'
    return bool(re.match(pattern, s)) and len(s) % 4 == 0
```
*Примечание:* Это необходимое, но не достаточное условие — случайная строка может подходить под паттерн. Декодирование и проверка на «осмысленность» результата даёт большую уверенность.

---

### 3. Как с помощью base64 проверить подлинность вводимых данных в форму пароля и логина?

**Base64 сам по себе НЕ обеспечивает аутентификацию/подлинность** — это просто кодирование, обратимое без ключа.

**Правильное применение в контексте авторизации:**
1. **Basic Auth:** `login:password` → base64 → заголовок `Authorization: Basic <base64>`. Сервер декодирует и сверяет с хранимым хэшем пароля. **Base64 здесь только для транспортной безопасности** (чтобы спецсимволы не ломали HTTP-заголовки).
2. **Токены (JWT):** Header.Payload.Signature — все части base64url. Подлинность проверяется **подписью** (HMAC/RSA), а не base64.
3. **Challenge-response:** Сервер шлёт случайный nonce, клиент возвращает `base64(HMAC(key, nonce))` — проверяется HMAC.

**Вывод:** Base64 используется для **представления** учётных данных/токенов в текстовом виде. Подлинность проверяется криптографическими средствами (хэши, MAC, цифровые подписи), а не самим base64.

| Формат | Алфавит | Энтропия Хартли | Энтропия Шеннона | Избыточность | Особенности |

### 5. Объяснить результат операции a ⊕ b ⊕ b. Где может найти применение такая операция?

**Результат:** `a ⊕ b ⊕ b = a` (исходное значение a восстанавливается полностью).

**Математическое обоснование:**
- XOR ассоциативен и коммутативен: `a ⊕ b ⊕ b = a ⊕ (b ⊕ b)`
- Для любого бита `x`: `x ⊕ x = 0`
- `b ⊕ b = 0` (нулевой вектор той же длины)
- `a ⊕ 0 = a`

**Применения:**
1. **Потоковые шифры (RC4, ChaCha20, AES-CTR):** Ключевой поток `b` XOR-ится с открытым текстом `a` → шифротекст `c`. Расшифровка: `c ⊕ b = a ⊕ b ⊕ b = a`. Один и тот же ключевой поток шифрует и расшифровывает.
2. **Одноразовый блокнот (One-Time Pad):** `b` — истинно случайный ключ длины ≥ `a`. Обеспечивает абсолютную секретность (по Шеннону).
3. **Контрольные суммы / RAID-5:** Параллельный XOR блоков позволяет восстановить упавший диск.
4. **Обмен значениями без временной переменной:** `a ^= b; b ^= a; a ^= b` (в низкоуровневом коде).
5. **Криптографические протоколы:** Diffie-Hellman, TLS — ключевой материал комбинируется через XOR.

### 6. Конвертация строк в base64

Даны строки (в hex-виде):
```
efd8b295a633908a3c0828b2
faea8766
4d72cde3aaa0
```

Интерпретируем как **сырые байты** (hex → bytes) и кодируем в base64:

| Hex-строка | Байты | Base64 |
|------------|-------|--------|
| `efd8b295a633908a3c0828b2` | 12 байт | `79iylaYzkIw8CIiy` |
| `faea8766` | 4 байта | `+uqHZg==` |
| `4d72cde3aaa0` | 6 байт | `TXLN46qo` |

**Проверка (Python):**
```python
import base64
print(base64.b64encode(bytes.fromhex("efd8b295a633908a3c0828b2")).decode())  # 79iylaYzkIw8CIiy
print(base64.b64encode(bytes.fromhex("faea8766")).decode())                     # +uqHZg==
print(base64.b64encode(bytes.fromhex("4d72cde3aaa0")).decode())                 # TXLN46qo
```

### 7. Найти значение b при известном a ⊕ b

Дано: результаты `a ⊕ b` для трёх разных строк `a` (один и тот же ключ `b`):
```
c1 = 1f180d1e1f04051c404c0f19
c2 = 1f180308050d024c030a4c18
c3 = 04094c1f18030009024c1c00
```

**Метод:** Так как `b` неизменно, `c1 ⊕ c2 = (a1 ⊕ b) ⊕ (a2 ⊕ b) = a1 ⊕ a2`. Но нам нужно найти сам `b`.

Возьмём две строки одинаковой длины. `c1` и `c2` — по 24 hex-символа = 12 байт. `c3` — 26 hex-символов = 13 байт (возможно, опечатка в условии, берём первые 12 байт).

**Находим b через свойство:** Если бы мы знали один `a`, то `b = a ⊕ c`. Но `a` неизвестны.

**Однако** — если предположить, что это пример «многократного использования ключа» (many-time pad), то XOR двух шифротекстов даёт XOR открытых текстов:
```
c1 ⊕ c2 = a1 ⊕ a2
```

Это позволяет восстановить `a1` и `a2` по частям (crib dragging), если известна структура plaintext (например, английский текст, пробелы = 0x20).

**Но в условии задачи подразумевается простое решение:** `b` — это **повторяющийся ключ** (один и тот же для всех трёх строк). Значит, длина `b` ≤ длины строк.

**Наблюдение:** Первые 2 байта `c1` и `c2` одинаковы: `1f 18`. Значит, `a1[0:2] ⊕ b[0:2] = a2[0:2] ⊕ b[0:2]` → `a1[0:2] = a2[0:2]`. Открытые тексты начинаются одинаково.

**Решение через системы уравнений:** Недостаточно данных для однозначного нахождения `b` без знания хоть одного `a`.

**Если это учебная задача с подвохом:** Возможно, `b` — это **нулевой вектор**? Тогда `c = a`, но строки разные — нет.

**Практический ответ:** Без знания хотя бы одного открытого текста `a` или предположений о его структуре (язык, формат) — **однозначно найти `b` невозможно**. Это и есть суть стойкости одноразового блокнота: при однократном использовании случайного `b` длина ≥ сообщения — криптоанализ невозможен. При повторном использовании `b` (many-time pad) — возможен crib dragging.

*Если в условии подразумевалось, что `a` — это известные строки (например, из задания 3), то нужно уточнить исходные данные.*
